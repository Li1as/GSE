## 实现

- `mail_tasks.py` 提供 create/show/answer/decide/resume/worker，使用已有 API 与模型配置；不接入 SMTP。
- 邮件和用户目标形成独立父任务，个人事实查询形成阶段一子任务。父子编号和初始子任务在同一 SQLite 事务提交，重启不丢关联。任务锁复用阶段一单机文件锁。
- 本次决定单独追问，相关性校验后保留用户原文；决定不写入长期资料。事实补充沿用 task/personal、冲突确认、缺失请求和归档恢复机制。
- 补充后自动检查所有子任务；直接从阶段一补充也可由邮件 worker 恢复。子任务 failed、needs_review、来源 unknown/stale 均不能直接作为齐全资料拟稿。
- 邮件快照与 EML 一致性校验后固化到父任务；显式传入的历史最多四封，校验账号和回复头关联。模型只接收正文与附件元信息，不接收附件字节、邮箱凭据或完整邮箱。
- 草稿记录版本、来源证据、子任务依赖、用户决定和模型。拟稿前后核对依赖一致性；资料更新使历史草稿 freshness=stale，显式 resume 重新准备。收件人建议由程序从邮件地址头生成，不让模型指定。
- 失败保存状态，显式 resume 重试；worker 只处理活动任务，空闲等待不轮询模型。本步无常驻进程、手机界面或发送行为。

## 验收方法

离线测试覆盖缺失事实与决定、无关回复拒绝、临时资料隔离、长期资料归档复用、请求归属检查、重复创建、重启恢复、阶段一入口补充后的父任务恢复、过时草稿、错误模型结构、虚构引用、附件内容限制、快照篡改与无关历史拒绝、冲突及失败子任务、草稿中断与决定修订。

真实 API 验收脚本 `live_mail_b_acceptance.py` 使用独立 `data/mail-b-live/<运行编号>/` 下的虚构资料、邮件和 SQLite。场景：通知要求“2026年春季验收课程QX91最终成绩”和“是否参加活动”；先提交无关回复，再临时补充 93 分，重新打开数据库后明确参加，生成有证据的草稿，最后发起独立任务验证临时成绩不可跨任务使用。

首次联网运行暴露提示词歧义：模型已接受补充，却因补充不是原成绩单而拒绝引用。已在阶段一系统提示词明确：已接受补充是有效独立证据，应标明“据用户本次补充”，不能因原文件未记载就判缺失或冲突。保留原始文件与补充来源的区别。

## 边界

模型对事实/决定分类、相关性和正文语义仍可能出错，程序校验结构、来源编号和版本，不宣称可以形式化证明每句话。草稿始终 requires_review，2C/2D 再提供编辑与精确版本确认发送。

需要附件正文或其他未提供上下文时，plan.blockers 阻止拟稿。本步没有附件分析工具或通用 blocker 交互入口；应核对目标和输入后建立新任务。历史快照的关系校验不等于完整会话重建。验收使用虚构邮件，不将测试事实写入真实个人信息库。
