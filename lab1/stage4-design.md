# 第四阶段：由任务 URL 驱动的 ehall 事务

## 目标与范围

第四阶段接入一种用户实际会办理的 ehall 事务，复用前三阶段已经具备的个人资料查询、补充请求、手机交互、持久任务、具体版本确认和中断恢复能力，完成“读取页面 → 准备资料 → 填写 → 核对 → 确认提交 → 保存结果”。

ehall 不采用阶段三邮件的持续采集模式。系统不轮询 ehall、不枚举可办事项、不自动分类事务，也不根据页面变化主动创建任务。用户提供具体任务 URL 是创建 ehall 任务和启动浏览器读取的必要条件。

用户发起任务时可以在 URL 之外提供一段简要口头描述，并可上传本次事务可能需要的附件。简要描述的性质与邮件父任务中的 goal 等任务级输入相同：

- 仅属于当前 ehall 任务，不自动写入长期个人资料、规则或偏好。
- 可帮助理解当前目标、页面语境和需要准备的内容，但不是个人事实的证据。
- 不代替页面读取、资料查询、用户决定或最终确认。
- 信息不足、含糊或与页面及资料冲突时，系统仍正常提出补充问题，不因已有描述而停止追问。
- 描述中的文字和页面内容都不能授权提交、扩大资料读取范围或绕过安全检查。

附件同样只属于当前任务。创建任务时可以先上传，页面读取后也可以按实际字段要求继续补充；Agent 应根据页面显示的必填项、类型、大小和数量限制判断哪些附件真正需要，不因用户预先上传而假定必须提交。附件内容哈希进入字段版本和最终确认，附件变化后旧确认失效。除 URL、简要描述和可选附件外，其余输入默认由 Agent 在读取页面后按实际字段追问，不预设额外的创建参数。

本阶段只实现用户主动发起的一种具体事务。资讯监控、事务推荐、自动发现待办、多事务通用识别和经验沉淀均不在第四阶段范围内。

## 与前三阶段的关系

阶段一的 `Assistant` 继续承担个人资料查询、来源定位、缺失项补充以及 task/personal 保存范围隔离。ehall 使用独立父任务关联这些资料子任务，不把表单业务写入资料查询器。

阶段二的邮件父任务、草稿版本与发送记录提供可复用的设计模式，但 ehall 任务不伪装成邮件任务。两者只共享资料接口、补充语义、单机锁、版本检查和“冻结内容后确认”的原则。

阶段三的增量收信、分类、去重和持续调度只服务邮件。ehall 不增加 monitor、classifier 或自动发现队列。需要恢复的只是用户已经创建的持久 ehall 任务和明确入队的浏览器工作，不是定期扫描网站。

现有手机网页继续作为统一交互入口。用户从手机粘贴任务 URL，可同时填写简要描述和上传可选附件；后续在同一网页查看进度、回答问题、修改字段、核对冻结版本和确认操作。

## 总体架构

建议保持一个后台应用内的多个业务模块，并将浏览器执行放在独立 worker 中，避免登录、加载和附件上传长时间占用 HTTP 请求线程。

- `ehall_tasks.py`：ehall 父任务、资料子任务、字段版本、状态转换和归档。
- `ehall_browser.py`：浏览器会话、允许域名、登录检测、页面读取和脱敏证据保存。
- `ehall_adapters/<事务名>.py`：一种具体事务的页面身份、字段、依赖、填表、提交和结果核对逻辑。
- `ehall_submit.py`：冻结预览、确认记录、提交意图、恢复和结果核对。
- `ehall_worker.py`：处理用户已创建任务对应的有界浏览器工作；不自行发现新事务。
- `mail_web.py`：在现有认证入口中增加 ehall API 和页面区域，注入 ehall 服务；本阶段不为改名而重构整个 Web 服务。

浏览器工具优先验证 Playwright。具体语言绑定和版本须在真实环境中验证后固定；浏览器配置、登录会话、Cookie、页面快照、截图和个人回执均属于本地私有数据，不提交 Git。

## URL 入口与页面边界

创建接口至少接受 `url`、可空的 `description` 和可空的 `attachments`。`url` 必填；没有 URL 时只返回输入错误，不创建任务，也不尝试搜索或推荐 ehall 事项。除可选附件外，其余事务字段由 Agent 读取页面后按实际要求查询或追问。

URL 在首次访问及每次跳转时都执行以下检查：

1. 只允许 HTTPS。
2. 主机必须位于显式配置的南京大学 ehall 与认证域名白名单中；不能使用字符串后缀近似匹配。
3. 禁止 URL 内嵌账号密码并限制长度；保留 SPA 路由所需的 fragment，但在公开摘要和日志中删除 query 与 fragment。
4. 登录跳转只允许到已配置认证域；跳往未知域名立即暂停。
5. 登录完成后由具体适配器验证页面标题、路径、稳定控件和事务标识。仅域名相同不足以证明页面正确。
6. 页面不符合预期时进入 `page_changed` 或 `needs_review`，不能让模型猜测按钮并继续。

用户提交 URL 后，系统可以在允许域内自动读取页面、查询必要资料、提出补充问题，并在信息齐全后填写和回读该项事务。该入口不授权最终提交；提交仍须对冻结版本单独确认。

## 具体事务适配器

每种支持的事务使用显式适配器，不通过通用模型自由操作浏览器。适配器至少提供以下能力：

- `identify(page)`：确认当前页面确实属于目标事务。
- `inspect(page)`：只读提取字段、当前值、必填标记、选项和字段依赖。
- `normalize(values)`：把网页和用户输入转换为稳定的数据表示。
- `validate(values, files)`：检查字段类型、必填项、枚举值、依赖和附件限制。
- `fill(page, values, files)`：填写或上传，但不点击最终提交。
- `read_back(page)`：从网页重新读取实际字段和派生值。
- `consequences(values)`：产生确认页必须展示的操作名称、关键后果和不可逆说明。
- `submit(page, binding)`：仅在冻结版本被明确确认后，对重新回读一致的精确控件执行一次最终提交并解析站点回执。
- `reconcile(page, record)`：从我的申请、状态页或回执页核对外部结果。

选择器优先使用稳定标签、控件名称、可访问属性和事务标识，并通过适配器版本管理变化。页面文本、HTML、附件名称和通知内容均为不可信输入，不能改变系统规则、允许域名、资料读取范围或确认要求。

## 任务模型与状态

ehall 父任务至少保存：任务编号、规范化 URL、适配器、用户简要描述、目标事务、页面摘要、字段版本、资料子任务、补充请求、用户决定、附件元信息、错误和创建时间。

用户一次提出多个独立高后果操作时（例如退选两门课），每个外部操作建立
独立 ehall 父任务。它们可以共用登录会话和同一入口 URL，但不共用字段版本、
确认或提交记录，避免一次确认意外授权多个退课动作。

建议在现有 `tasks.sqlite` 中增加独立表：

- `ehall_tasks(id, adapter, payload)`：当前父任务状态与字段版本。
- `ehall_previews(id, task_id, version, fingerprint, payload)`：冻结待确认内容。
- `ehall_submissions(id, task_id, preview_id, status, payload)`：每次外部执行意图及结果。
- `ehall_task_actions(task_id, action, acted_at, payload)`：归档、恢复和人工处置。

JSON payload 延续现有持久化方式；外部执行记录与任务当前状态分开保存，不能只在父任务上写一个“已提交”标志。

状态至少包括：

- `new`：已保存 URL 和描述，尚未读取页面。
- `inspecting`：正在只读识别页面与表单结构。
- `planning` / `preparing`：正在确定资料查询、决定和字段映射。
- `waiting_input`：等待资料补充或用户决定。
- `ready_to_fill` / `filling`：输入齐全，正在试填和回读。
- `needs_review`：页面变化、冲突或业务限制需人工核对。
- `preview_ready`：已有可编辑、可冻结的字段版本。
- `confirmed`：某个具体 fingerprint 已由用户确认。
- `submitting`：已记录执行意图，正在进行外部操作。
- `succeeded`：已取得能够支持成功判断的回执或状态。
- `failed`：明确未提交且错误允许重新准备。
- `unknown`：可能已提交，外部结果尚不能确认，禁止自动重试。
- `archived`：结果和审计记录保留，默认列表隐藏。

`login_required`、`session_expired` 和 `page_changed` 作为明确暂停原因保存，不应被普通自动重试吞掉。

## 资料查询、补充与字段编辑

读取页面后，适配器先得到结构化字段与页面要求，再由任务层结合用户简要描述决定本次真正需要查询的个人事实和需要用户决定的事项。只把当前事务必要的字段交给资料模块，不加载整个个人资料库。

资料子任务的 completed、waiting_input、needs_review 和 failed 语义沿用阶段一。来源过时、事实冲突或真实缺失时不能当作字段已准备完成。是否申请、是否接受后果、是否披露某项资料等意愿必须作为当前任务决定，不能从个人资料或简要描述中推断。

手机端允许用户直接编辑最终表单字段。每次保存生成新版本并使用乐观版本号；旧页面不能覆盖新版本。一次字段修改仅影响当前任务，不自动形成长期资料。若用户明确选择 personal 范围补充事实，继续沿用阶段一的归档与冲突检查。

附件使用内容哈希保存，记录文件名、大小和 SHA-256。提交前重新读取并校验字节；文件丢失、变化、成为符号链接或超过适配器限制时使预览失效。页面要求无法安全处理的文件类型进入人工核对。

## 试填、冻结预览与确认

资料和决定齐全后，worker 打开用户原 URL，验证页面身份，填写字段和附件，但不点击最终提交。随后必须从页面回读实际值，包括网页自动填充、格式化和字段依赖产生的派生值。

冻结预览至少包含：

- 事务名称、规范化入口和适配器版本。
- 全部最终字段及其回读值，包含影响结果的只读或派生字段。
- 附件名称、大小和内容哈希。
- 页面身份和结构版本摘要。
- 关键后果、提交按钮语义和已知不可逆性。
- 字段版本、必要资料来源和当前任务决定。

上述内容采用稳定序列化计算 `fingerprint`。确认记录绑定任务、预览编号、字段版本和 fingerprint。任何字段、附件、资料来源、用户决定、页面结构、派生值或适配器版本变化都使旧确认失效，必须重新试填、回读和确认。

用户确认只授权当前冻结版本的一次提交。确认后不再调用模型改写字段或决定操作。

## 执行、恢复与结果核对

外部执行不能依赖提示词约束，而由程序状态与适配器接口共同限制：只有当前预览仍有效且状态为 confirmed 时，才能进入一次性执行路径。

### 决策记录：课表退课在确认后直接提交

自 2026-09-16 起，取消“人工操作交接”。每门课仍是独立 ehall 父任务，需分别生成冻结预览并分别确认。预览明确展示课程名等关键字段、附件、操作后果和 fingerprint；用户勾选确认后，系统立即把该冻结版本加入提交队列。worker 重新打开原 URL、核对页面结构、课程稳定编号、课程名和回读值一致后，点击精确课程的“退课”入口一次，再点击内容与课程名一致的站点“确定”按钮一次。

站点固定退课请求返回成功码且 `TS == "0"` 时，保存脱敏回执并记为 `succeeded`；站点返回明确业务错误时记为 `failed`。进入 `before_click` 后发生超时、断网、进程退出或回执无法解析时记为 `unknown`，禁止自动重试。当前课表页只能证明“退课控件当前是否可见”，因此后续只读核对不会仅凭控件消失宣称成功。

课表可能先显示“提示 / 上课时间冲突信息”模态窗。提交预检只能在标题、三类冲突信息标识和唯一“关闭”按钮都匹配时关闭它；未知遮挡弹窗必须停止，不使用强制点击或 JavaScript 绕过。打开并核对“是否确认退出<课程名>”属于可安全失败的提交前阶段；只有随后的“确定”按钮才是 `before_click` 所保护的不可重试边界。

真实退课与可控测试共用下列执行顺序：

执行顺序为：

1. 获取 `ehall:<task_id>` 单机文件锁，检查同一任务没有 submitting、unknown 或 succeeded 记录。
2. 持久化 submission 记录，状态为 `submitting`，阶段为 `before_open`。
3. 打开原 URL，验证登录、域名、页面和适配器版本。
4. 关闭已知非事务提示窗，重新填写并回读，确认得到的 fingerprint 与用户确认版本完全一致。
5. 打开退课确认框并核对精确课程名；此阶段失败明确没有提交。
6. 持久化阶段 `before_click`，随后只调用一次适配器 `submit`点击最终“确定”。
7. 获取明确回执或可验证成功状态后记为 `succeeded`；明确未执行时才可记为 `failed`。
8. 最终点击后出现超时、断线、进程退出或含糊页面时记为 `unknown`。

SQLite 无法与外部网站组成原子事务。进程重启发现 submission 停在可能已经点击的阶段时必须转为 unknown，不得再次点击。unknown 只能调用适配器的只读 `reconcile` 查询申请列表、状态页或回执；没有可靠外部判据时交由用户处理。

回执记录保存观察时间、事务标识、申请编号、状态、页面摘要及相关证据哈希。截图和完整页面位于 Git 忽略的私有目录，对外接口只返回必要摘要。归档不删除任务、字段版本、确认、提交意图或回执证据。

## 登录、凭据与运行边界

### 决策记录：只使用二维码登录

自 2026-09-16 起，ehall 自动化不再接受、读取、保存或填写统一认证账号密码。访问用户 URL 后如果进入统一认证页，程序只定位站点生成的登录二维码，截取二维码元素并临时保存到固定私有路径 `data/ehall/login/qr.png`，等待用户使用微信或南京大学 App 扫码确认。

4A 由用户在运行主机上打开该临时图片后手动扫描；4C 再通过现有 Bearer token 保护的手机页面提供二维码图像。二维码是短期登录凭证：文件和状态元数据权限为 600，同一时间只允许一个扫码登录，二维码刷新时原子替换，登录成功、等待超时或任务失败后立即删除，不进入 SQLite、日志、截图归档或 Git。

程序不解析二维码内容、不把它交给模型、不尝试滑块、验证码或其他绕过方式。二维码登录失败或要求额外人工确认时进入 `login_required`，用户显式重试。扫码成功后的 Cookie 和浏览器会话只保存在权限受限、被 Git 忽略的独立浏览器资料目录，用于继续访问用户原 URL；会话过期后重新生成二维码。

浏览器用户目录和认证状态单独保存在权限受限且被 Git 忽略的目录。会话失效时任务进入 login_required 或 session_expired；用户重新扫码后显式恢复。页面中的登录提示不能被误判为普通表单字段。

浏览器 worker 只消费用户已经创建或明确恢复的任务。它可以持续运行以恢复这些持久任务，但不能借此扫描 ehall、发现新事项或替用户判断是否办理。

## 手机 API 与交互

在现有 Bearer token、同源检查和 no-store 响应基础上增加独立接口：

- `POST /api/ehall/tasks`：提交 URL、可空简要描述和可选附件，创建任务并自动入队开始读取、资料查询和准备。
- `GET /api/ehall/tasks`：查看未归档任务。
- `GET /api/ehall/tasks/<id>`：查看状态、字段、来源、补充问题和审计摘要。
- `POST /api/ehall/tasks/<id>/answer`：回答资料补充，明确 task/personal 范围。
- `POST /api/ehall/tasks/<id>/decide`：回答本次任务决定。
- `POST /api/ehall/tasks/<id>/edit`：按字段版本保存用户修改。
- `POST /api/ehall/tasks/<id>/prepare`：在暂停、修改或失败后显式重新准备；初次创建不需要再调用。
- `POST /api/ehall/tasks/<id>/preview`：生成冻结预览。
- `POST /api/ehall/tasks/<id>/confirm`：确认指定 fingerprint。
- `POST /api/ehall/tasks/<id>/submit`：把已确认且仍有效的冻结版本加入一次性提交队列。
- `POST /api/ehall/tasks/<id>/reconcile`：只读核对结果不明记录。
- `POST /api/ehall/tasks/<id>/archive` 与 `restore`：管理列表可见性。

创建、重新准备、确认和提交应在页面上使用不同按钮和状态说明。粘贴 URL 会启动该事务的读取、资料查询和非最终填写，但不等于授权提交。手机断开或 HTTP 响应丢失不取消已经持久化的工作。

## 分步实现

### 4A：URL 入口与真实只读探测

选定一种真实事务，验证浏览器工具、用户登录、URL 白名单、页面身份、会话失效和只读字段提取。只允许用户提交 URL 后访问；不填写、不上传、不提交。真实页面和截图保存在隔离私有目录。

### 4B：事务父任务与资料准备

实现 ehall 父任务、适配器字段模型和资料子任务。使用离线合成页面验证字段提取、资料缺失、补充恢复、任务级简要描述和 task/personal 隔离。本步不操作真实表单。

### 4C：手机编辑与浏览器试填

增加手机任务创建、追问、字段编辑和附件管理。对真实事务执行填写与页面回读，但在程序接口和适配器中禁用最终提交。验证字段依赖、版本冲突、登录过期和页面变化。

“我的课表”页面对退课没有独立的可编辑表单，而是直接暴露每门课的
“退课”动作。因此该适配器在 4C 的“试填”只表示：按用户选定的教学班
ID 唯一定位动作控件，重新读取课程名和动作类型并校验一致性。此过程不调用
`click()`、不派发 DOM 事件、不调用站点 JavaScript。真正点击“退课”就是
该事务的高后果外部操作，必须留到 4D 冻结预览和明确确认之后。

### 4D：具体版本确认与保守提交

实现冻结预览、fingerprint、确认记录、submission 状态机和结果核对。用可控假站点覆盖双击、中断、超时和回执查询；当前两个真实退课任务各自冻结和确认，确认后由 worker 对精确绑定的课程执行一次提交。

### 4E：完整流程与异常验收

对选定真实事务走完 URL 发起、资料查询、手机补充、字段修改、试填、确认、提交、回执和归档。完成前三阶段全部回归，并记录真实验收未覆盖的外部异常，不把模拟结果写成真实站点能力。

4E 已补充 ehall 任务归档/恢复、列表过滤、审计动作、终态展示，并增加“提交成功 → 归档 → 重启后证据保留 → 恢复”的可控端到端测试。真实站点完整验收仍以取得成功回执为准；若暴露新的弹窗或回执结构，只在取得脱敏证据后更新适配器和回归用例。

## 验收标准

- 没有用户提供的 URL 时，不访问 ehall、不发现或创建事务。
- URL、简要描述和可选附件在重启后保留；描述和附件只作用于当前任务，且不会阻止按页面实际字段追问。
- URL 跳往未知域名、登录失效或页面身份不符时明确暂停。
- 至少一种真实事务能够完成资料查询、材料准备、表单填写和页面回读。
- 缺少资料时能从手机补充并继续；用户可以直接修改最终字段，旧版本不能覆盖新版本。
- 未确认不能提交；字段、附件或页面变化后必须重新确认。
- 实际提交内容与冻结预览一致，提交阶段不调用模型改写。
- 双击或并发不会产生第二次提交；点击后超时或重启进入 unknown，不自动重试。
- 成功结果有申请编号、状态或其他可靠证据；结果不明优先只读核对。
- 回归测试证明阶段一资料、阶段二邮件闭环和阶段三持续收信行为未被破坏。

## 明确保留边界

- 不持续监控、搜索、推荐或分类 ehall 事务。
- 不从邮件自动创建 ehall 任务；跨工具自动组合留待后续阶段。
- 不自动推广用户简要描述、字段修改或一次性决定为长期规则。
- 不让模型自由浏览和决定最终点击目标。
- 不处理退课、撤销申请等高风险事务的自主决策。
- 不承诺绕过扫码、多因素验证、验证码或站点反自动化机制。
- 不把本地数据库状态等同于外部网站已经成功受理。
