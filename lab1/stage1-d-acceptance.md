# 小步 D 验收与阶段一完整性评估

日期：2026-09-14。实现：[persistence.py](persistence.py)、[assistant.py](assistant.py)。

## D 交付

1. 文件哈希清单：每次新查询读取当前 Markdown；发布答案前检测变化，历史结果标记 current/stale/unknown。
2. 任务恢复：worker 启动扫描、持续轮询和人工 resume；从原目标、已接受补充及当前资料重新检索。
3. 单机互斥：Linux/WSL 的 flock 防止同一任务同时执行，进程退出后自动释放。
4. 归档待办：SQLite 接受记录与 archives 待办同事务提交，Markdown 通过 fsync 和原子替换发布；中断可重做未完成步骤。
5. 幂等保护：已发布文件的后续修改／删除不会被旧收据恢复；待发布路径冲突时保留现场并报告。
6. 请求恢复：关联记录与任务同事务保存，缺失投影可重建，保留用户尚未提交的回复草稿。
7. 有界重试：每次查询仍限制 API 时长、输出和步骤；自动执行最多三次、失败退避；不反复调用未变化的等待任务。

## 离线验收

命令：`python3 -m unittest discover -s lab1 -p 'test_*.py' -v`。

**40 项通过**：16 项 B 测试、12 项 C 测试、12 项 D 测试。D 的故障注入使用隔离临时资料与可控客户端：

| 场景 | 验收结果 |
| --- | --- |
| 接受补充后、文件写入前中断 | 新实例补写一份文件，恢复同一任务；重复恢复不重复执行 |
| 文件已原子替换、发布标记前中断 | 新实例识别现有文件并完成标记，不重复改写文件 |
| 用户修改／删除已发布补充 | 恢复和重复回复均不覆盖新值或复活被删文件 |
| 待发布路径已存在不同内容 | ARCHIVE_CONFLICT，原内容保持不变 |
| 等待任务期间新增 Markdown | 自动重查同一任务，原请求标记由资料更新解决 |
| 等待任务资料无变化 | 不调用模型 |
| 结果已保存、请求创建前中断 | 恢复补齐请求关联与 Markdown，无重复请求 |
| 请求投影丢失／存在未提交草稿 | 丢失文件重建，已有草稿保留 |
| 模型查询期间资料变化 | DATA_CHANGED，旧快照答案不发布 |
| 网络失败退避与预算 | 未到重试时间不执行，达到预算不无限调用 |
| 真正终止持锁子进程 | 存活时第二执行者跳过，终止后锁释放，原任务可恢复 |
| 人工 resume | 保留任务编号与同一待补充请求 |

文件一致性故障使用 SystemExit 在确定的写入边界注入；锁释放测试实际启动并终止子进程。没有模拟磁盘硬件损坏或数据库文件损坏。

## 使用边界

- 必须运行 `python3 lab1/assistant.py worker --interval 15` 才会持续恢复和监测等待任务；未安装系统自启动服务，未留下常驻进程。
- 采用单机 Linux/WSL 文件锁，不支持多主机共同运行；运行环境为 Python 3.8+。
- 恢复重新执行有界检索，不承诺复用中断时已发生但未记账的模型调用；可能多消耗一次 API 请求，但不重复已发布资料写入。
- 模型的事实支持、相关性和冲突判断仍需案例验收。引用身份校验不能证明所有自然语言推理正确，未宣称零幻觉。
- 已完成答案不因文件变化自动重新生成；查看时标记 stale，需要最新答案可 query 或 resume。
- 旧版 C 收据按已发布迁移，无法从旧日志判断的缺失文件不自动复活；新版本的待发布写入由 archives 精确记录。
- 数据库损坏、跨机器协调、外部邮件／表单的幂等性不在本阶段范围。
