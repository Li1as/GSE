# 第三阶段：持续收信、分类、去重与可靠恢复

## 目标与范围

将阶段二的人工选信入口扩展为持续收信：脚本发现邮件、持久化采集、分类，再复用个人资料查询、补充、拟稿、手机编辑和具体版本确认发送。Python 标准库与 SQLite 足够，不引入外部消息队列或 Agent 轮值。

3A 已实现增量采集与恢复，3B 已实现分类和人工纠正，3C 已实现统一任务入口、来源绑定、入口去重和单次任务写作风格约束，3D 已实现往来更新与发送边界，3E 已实现持续调度与手机管理界面。采集程序不调用模型或发送接口，分类程序只在处理尚未分类的 ready 邮件时调用模型。所有快照、队列、游标、分类记录和私有验收证据放在被 Git 忽略的 data/。

## 模块与流程

- mail_monitor.py：只读 IMAP 增量发现、正文采集、轮询、连接重试与 CLI。
- mail_inbox.py：SQLite 扫描状态、稳定收件身份、持久待办与恢复。
- mail_classifier.py、mail_pipeline.py：分类、人工纠正、稳定来源绑定及自动任务编排。
- mail_tasks.py、assistant.py、mail_send.py：继续承担资料查询、邮件准备及用户确认发送。

流程：发现 UID → 收件记录与待办落盘 → 正文快照 → 分类。分类为无需回复、需要判断、需要回复；后两者分别等待用户或创建/复用邮件任务。分类结果与执行状态分开，API 失败不能归为无需回复。

## 3A：增量采集

第一版单账号、单机、INBOX，默认每 60 秒一轮，每轮采集最多 50 封。默认首次从现在开始，以只读 SELECT 返回的 UIDNEXT-1 建立基线；历史补录必须显式选择。既有游标不能因重启或再次传初始化参数重置。

每个账号端点与文件夹维护 UIDVALIDITY、发现边界、首次基线、最近成功扫描时间、连续错误与下次重试时间。按有界 UID 数值区间升序搜索，过滤服务端越界结果；空区间也可推进，UID 允许有空洞。不使用“最近 N 封”截断，也不依赖已读标志判断处理完成。

同一事务插入该区间所有发现记录并推进扫描边界。采集在事务提交之后执行，失败记录独立重试；进程在事务前后中断不会跳过已发现邮件。记录身份为账号端点、文件夹、UIDVALIDITY、UID；Message-ID 不承担采集唯一性。数据库唯一约束与单机文件锁同时保护重复运行。

快照使用现有 EML/JSON 发布方式，恢复时校验两份文件内容及 IMAP 身份，完整则复用；半成品重新采集。超大、无法解析、已删除或超过下游正文上限的邮件保留人工处理记录，不阻塞后续邮件。断网有限退避；认证失败暂停，用户修正配置后显式恢复。UIDVALIDITY 改变时暂停，必须核对新代标识后明确重建基线，旧记录保留；不能自动使用旧 UID 读取新邮件。

同一轮发现与采集都有上限；轮询停止后所有状态保留。3A 不安装后台服务，用户显式运行 run 才持续监控。服务器在采集前已删除的邮件只能报告无法读取，不能承诺恢复已不存在的正文。

## 3B：分类和人工纠正

分类前仅提供当前邮件、必要往来与明确配置的处理偏好，不先读取整个个人资料库。输出类别、行动请求及原文依据、理由、建议目标、用户待决定事项与上下文限制。

“需要答复”不等于可以替用户决定是否参加。no-reply、抄送、群发仅是线索，不能单独证明无需行动。无法判断时在手机提出具体问题；无需回复的邮件仍可查看和改判。用户单次纠正保存为记录，不自动泛化永久规则，经验总结留在阶段五。

当前实现位于 `mail_classifier.py`。它只选择 3A 中 status=ready 的快照，发送当前邮件以及通过回复头识别的最多四封相关历史给模型；不读取个人资料库、邮箱凭据或附件字节。分类结果绑定 EML 哈希和分类策略版本，状态独立保存于 `mail_classifications` 表。

模型输出必须通过程序校验：类别仅限 reply_required/no_reply/user_review，理由与置信度必填，行动依据必须逐字来自当前正文；需要回复时必须给出建议任务目标，需要判断时必须提出具体问题。结构错误与暂时 API 故障有限重试，认证等不可自动恢复的错误进入 failed，任何失败都不能生成 no_reply。

分类完成后重复扫描不再调用模型。来源或策略变化进入 needs_review，必须显式 retry；人工 correct 只改变当前有效分类，保留模型原判及历史，不调用模型、不创建邮件任务、不生成长期规则。当前提供 CLI 查看和纠正；手机端列表与纠正界面仍在 3E 实现。

## 3C：统一任务入口和去重

自动处理和手动网页入口统一经过稳定收件记录关联业务任务。稳定身份包含账号端点、文件夹、UIDVALIDITY 和 UID；任务库保存明确的来源收件 ID、来源绑定和幂等创建记录。同一身份的自动与手动入口复用一个任务，即使目标文字不同也不重复建任务；仅内容哈希相同但 UID 不同的邮件仍视为不同来源。

任务创建与来源绑定在同一数据库事务和同一来源锁内完成，中断或并发重试仍找到同一任务。分类变化更新同一绑定：reply_required 创建或恢复准备流程，no_reply 和 user_review 暂停自动任务；暂停状态会阻止生成发送预览，不能通过另建任务绕过发送保护。

无历史邮件使用简洁、礼貌、偏正式的默认风格，并跟随来信的主要语言。程序不推断老师、学长、同事等关系，不自动添加签名、联系方式、表情或整段引文。混合语言或无法判断语言时，只创建一个本次任务的风格决定；模型不得另行改写或重复该问题。已有往来时将有限历史作为风格依据，但一次草稿修改不自动沉淀为长期偏好，长期风格学习留在阶段五。草稿主题规范化，已有 Re: 前缀时不重复添加。

当前 3C 不处理新往来令旧草稿失效、手机分类队列或持续业务调度，这些分别属于 3D 和 3E。完整实现与首次失败修复见 [3C 验收记录](stage3-c-acceptance.md)。

## 3D：往来更新和发送边界

优先从回复头、本地快照、本地已发送归档寻找往来，服务器 Sent Messages 只是补充来源。继续保留有限历史（当前最多四封）及不完整说明。缺历史仅在确实影响回复时阻塞。

为相关会话维护本地版本，新往来到达后提示未发送任务核对，保留用户编辑，使旧发送预览失效。草稿及发送检查纳入已知往来版本；用户选择纳入并重新准备，或说明无关。不能保证尚未被扫描到的新邮件已参与检查。临时资料不因会话关联自动跨任务复制。

当前实现以账号、回复头中的 Message-ID、In-Reply-To 和 References 建立本地往来标识。新邮件与未完成任务相关时，不创建第二个任务，也不立即调用拟稿模型；程序在同一 SQLite 事务中保存来源关联与待核对更新，并递增往来版本。仅主题相同或正文哈希相同不会建立关联，相同内容但不同 UID 仍是不同投递。

待核对期间保留当前草稿和所有历史版本，但草稿依赖摘要已过时，编辑、确认和发送均被阻止。选择“纳入”后，新邮件成为当前回复对象，原邮件进入最多四封的历史，用户亲自编辑的上一版草稿作为受限输入参与重新拟稿；选择“忽略”后，正文、收件人与附件原样复制为新版本，并绑定新的往来版本。两种选择都会使旧发送预览失效。

已由 SMTP 接收的旧任务可以在对方新回复后建立后续任务；同一往来中存在 `sending` 或 `unknown` 记录时，任何其他任务都不能生成发送预览。此保护不声称邮箱服务器会去重，也不会自动重发或自动发送。详细结果见 [3D 验收记录](stage3-d-acceptance.md)。

## 3E：持续调度与手机交互

模型处理与采集分开，持久待办按变化、到期重试时间和等待时长调度，避免前几个 waiting_input 任务占满额度。无变化的等待任务不调用模型。网络/API 暂时失败有限退避，认证失败暂停，已发送或结果不明不自动发送。

网页增加收件处理列表（待判断、准备中、待补充、待审阅、无需回复、失败）、分类理由与纠正、最近扫描成功时间、积压、暂停/恢复/手动扫描。改判无需回复时暂停准备，保留草稿和历史。

无需回复的邮件另有“已处理”状态：该状态与分类解耦，不改变模型判断或邮箱已读标志，只控制默认队列可见性。已处理记录绑定分类版本；分类改变时重新显示，并可从已处理列表手动恢复。人工纠正为无需回复后适用同一规则。

已完成回复采用独立的“任务归档”状态：只有存在 SMTP `accepted` 记录的任务可归档；归档不删除草稿、冻结版本、确认或发送审计，并要求恢复后才能继续操作。归档任务同时从默认任务列表和自动邮件队列隐藏，新来信仍按新的来源身份创建或更新任务，不由旧归档记录吞掉。两个历史区分别按操作时间倒序展示最近 10 条；完整记录继续保存在 SQLite 中。

当前实现由 `mail_scheduler.py` 统一执行有界的“采集 → 分类 → 任务分派”周期。调度状态、暂停标志、失败次数、退避时间和最近成功时间保存在 SQLite；重启后继续。每轮分别限制采集、分类和分派数量，已处理分类通过 `mail_dispatches` 游标跳过，因此旧的等待任务不会反复占用额度，空闲轮次不会调用模型。网络或 API 故障采用有限退避；认证、UIDVALIDITY 和人工核对状态沿用 3A—3D 的保守暂停规则。

手机网页提供自动化状态、当前代积压、分类统计、收件处理列表、分类理由、关联任务、单封邮件分类纠正，以及暂停、恢复和立即执行一轮。网页控制和独立调度进程共享文件锁与 SQLite 状态；任何入口都不会自动确认或发送草稿。

项目提供 scheduler 与 web 两个 systemd 用户服务模板，但不自动安装或启用。服务运行仍依赖主机联网、不中断休眠，以及 WSL/systemd 和既有 Windows 端口转发持续可用。详细结果见 [3E 验收及前三阶段总结](stage3-e-acceptance.md)。

## 小步验收

| 小步 | 核心验收 |
| --- | --- |
| 3A | 超过一批的新信不漏；只读及未读保持；空洞/边界过滤；重复、并发与崩溃恢复；异常邮件不堵队列；认证暂停与 UID 代变更保护 |
| 3B | 三类判定可追踪和纠正；不确定追问；失败不误判为无需回复 |
| 3C | 自动和手动入口不重复建任务；创建/关联中断恢复；分类版本变化不产生第二回复任务 |
| 3D | 更正邮件令旧预览失效；用户编辑保留；跨任务不能绕过结果不明保护 |
| 3E | 持续积压清空、断网重启、调度公平、空闲零模型调用、整个流程回归 |

自动测试使用隔离合成邮件和可控 IMAP/模型/SMTP；真实 3A 验收只读，使用隔离状态验证当前服务器 UID 增量、快照一致性和 FLAGS 保持，不改生产监控起点。真实新信到达和无法制造的服务器变化需要单独标注，不把模拟当作真实验证。实际发送仍需用户在网页确认具体内容。

第三阶段 3A—3E 已按上述边界完成。阶段三的最终验收为 169 项自动测试通过，并完成真实联网“有新工作一轮 + 紧接空闲一轮”的验证；第二轮没有分类或分派。运行环境和长期驻留限制见 3E 验收记录。
