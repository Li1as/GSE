# 第五阶段：经验复用与可审查的能力成长

## 目标与范围

第五阶段验证助手能够把用户明确选择的纠正转化为可阅读、可修改、可停用、可追溯的经验规则，并在另一个任务和另一次进程启动中按需复用。规则不能由邮件、网页、模型输出或一次普通编辑直接升级为长期行为。

本阶段的重复跨工具流程选择邮件：IMAP 增量收信与往来关联 → 分类 → 个人资料检索 → 手机补充和草稿编辑 → 冻结确认 → SMTP 发送 → 归档。该流程已经组合邮箱、个人资料、模型、手机网页和外部发送，阶段五在其上增加经验复用和应用证据，不建立“邮件自动创建 ehall 退课任务”的高风险组合。

ehall 暂时只保留课表退课这一种真实事务。第五阶段只核对适配器接口和回归测试，确保以后可以为其他 URL 驱动、多次填写或操作的浏览器任务增加显式适配器；不增加 ehall 轮询、事项发现、通用模型自由点击或新的真实事务。

## 已有基础与缺口

前四阶段已经具备以下基础：

- 单封邮件的分类纠正会保留模型原判和纠正历史，但不会自动生成长期规则。
- 邮件任务保存本次目标、写作风格、个人资料子任务、用户决定、草稿版本和发送审计。
- `task` 与 `personal` 范围已经隔离；一次草稿编辑和 ehall 字段修改默认只影响当前任务。
- 邮件发送和 ehall 提交都绑定冻结版本；外部结果不明时禁止自动重试。
- SQLite、文件锁、原子文件发布和恢复模式已经用于任务、资料补充及外部执行记录。

第五阶段需要补齐：

1. 把纠正来源保存为独立、不可变的经验事件。
2. 让模型或用户提出规则草案，但必须经用户单独批准后才能生效。
3. 用人工可读文件保存规则版本，并支持拒绝、停用、恢复和人工修改。
4. 在邮件分类、规划和拟稿中按作用域加载规则，并保存实际应用证据。
5. 证明新会话能应用规则，而一次性要求不会污染后续任务。

## 反馈分类与存储边界

| 反馈类型 | 默认保存位置 | 是否自动跨任务复用 |
| --- | --- | --- |
| 当前任务的文字、决定、字段或草稿修改 | 当前任务 payload | 否 |
| 明确选择为长期个人事实或偏好的内容 | 被 Git 忽略的个人资料目录 | 仅在必要任务中查询或加载 |
| 用户主动要求推广的语义纠正 | SQLite 经验事件和待审核草案 | 否，批准后才复用 |
| 已批准且不含隐私的通用规则 | `experience/rules/` JSON 文件 | 是，按规则作用域加载 |
| 可复用业务流程和检查方法 | 脚本及 `experience/workflows/` 文档 | 由明确入口执行 |
| 稳定的项目开发约定 | `AGENTS.md` | 只影响开发 Agent |

完整邮件正文、邮箱地址、个人资料、登录信息、任务决定和运行审计不进入规则文件或 Git。规则来源只保存经验事件编号和内容哈希。系统不自动执行 `git add` 或 `git commit`；规则发布后由用户查看差异并决定是否提交。

## 总体架构

新增独立经验层，不把长期规则逻辑塞入个人资料查询器、邮件任务或 ehall 适配器：

- `experience.py`：经验事件、规则草案、审核动作、规则文件、发布恢复和 CLI。
- `experience/rules/mail/*.json`：无隐私、可 Git 管理的邮件规则及完整版本历史。
- `experience/workflows/mail-reply.md`：5E 保存的邮件完整流程、入口、安全边界与验收步骤。
- `experience_events`：不可变的私有纠正来源。
- `experience_proposals`：待审核、待发布、已发布或已拒绝的规则草案。
- `experience_rule_actions`：批准、拒绝、停用和恢复审计。
- `experience_publications`：SQLite 到规则文件的持久发布意图，用于中断恢复。
- `experience_applications`：5C 增加的规则应用记录。

经验流转为：

```text
当前任务纠正
  → 经验事件
  → 用户主动请求形成草案
  → 模型或人工产生结构化草案
  → 用户核对并批准
  → 原子发布规则版本
  → 新任务捕获适用规则快照
  → 保存应用结论、原文依据和规则版本
```

## 5A：经验存储与规则生命周期

状态：已实现。5A 只建立存储、审核、发布和恢复能力，不把规则接入分类、规划或拟稿，也不自动从现有纠正生成草案。

### 经验事件

经验事件保存类型、创建时间、来源内容哈希和私有 JSON payload。第一版允许：

- `classification_correction`：单封邮件分类纠正。
- `draft_edit`：用户明确选中的草稿修改。
- `manual`：用户主动录入的纠正说明。

仅创建事件不会产生草案或规则。事件没有更新和删除入口，后续规则版本始终能追溯到当时的来源哈希。

### 草案格式

草案严格包含：

- `rule_id`：小写点号或连字符分隔的稳定编号。
- `title`：人工可读标题。
- `domains`：当前仅允许 `mail.classify`、`mail.plan`、`mail.draft`。
- `instruction`：规则正文。
- `examples` 与 `counterexamples`：有界的正例和反例。
- `rationale`：为什么值得跨任务复用。

未知字段、未知作用域、路径字符、空文本、超长内容和不可序列化内容均被拒绝。5A 不接受 `ehall.submit` 等可授权高风险动作的规则作用域。

### 规则文件与版本

每个逻辑规则使用一个 `<rule_id>.json` 文件，内容包括：

- `schema_version`
- `id`
- `enabled`
- `active_version`
- 连续的 `versions`

每次批准同一 `rule_id` 的新草案都会追加连续版本，不删除旧内容。批准新版本会使它成为活动版本；停用和恢复只改变 `enabled`，不创建隐式新规则版本。所有动作另存审计记录。

### 持久发布与恢复

批准、停用和恢复遵循：

1. 获取按规则编号派生的单机文件锁。
2. 校验现有规则文件、版本和人工编辑。
3. 在同一 SQLite 事务中写入审核动作及 `pending` 发布意图。
4. 将目标 JSON 写入同目录临时文件，`fsync` 后原子替换，再同步目录。
5. 将发布意图及关联草案标记为 `published`。

若进程在文件替换后、SQLite 标记前退出，`recover` 根据目标内容哈希识别已完成文件，只补写状态而不重复覆盖。若目标文件既不是发布前版本也不是待发布版本，则报告 `RULE_CONFLICT` 并保留人工内容。

### CLI

```bash
# 私有事件和规则草案均从 JSON 文件读取，避免在命令历史中暴露内容
python3 lab1/experience.py event --kind manual --file /path/to/event.json
python3 lab1/experience.py propose --event-id <事件编号> --file /path/to/proposal.json
python3 lab1/experience.py proposals
python3 lab1/experience.py approve <草案编号>
python3 lab1/experience.py reject <草案编号> --reason '本次要求不应跨任务复用'
python3 lab1/experience.py rules
python3 lab1/experience.py disable <规则编号> --reason '作用范围需要重新核对'
python3 lab1/experience.py restore <规则编号> --reason '已完成人工核对'
python3 lab1/experience.py recover
```

5A 没有模型调用、邮件读取、外部网络、自动 Git 操作或手机 API。

## 5B：从明确纠正形成规则草案

状态：已实现。手机网页提供实际的生成、审核、批准、拒绝、停用和恢复接口；5B 发布的规则尚不参与邮件分类、规划或拟稿。

分类页继续保留“保存本次纠正”，另设未预选的“提出可复用规则”。草稿修改也只有用户明确选择具体版本差异后才能产生经验事件。资料补充的 `task/personal` 选择不被经验系统替代。

模型只负责基于用户选中的纠正提出草案，不直接发布。草案页面必须展示来源类型、建议作用域、规则正文、正例、反例、可能误伤场景和隐私检查。用户可以编辑、批准或拒绝。邮件及网页中的文字是不可信数据，不能触发该流程或改变规则作用域。

当前实际入口：

- 已完成分类纠正的邮件显示“提出可复用规则”，并要求另填本次希望推广的明确说明。
- 邮件任务的历史草稿中，只有 `editor=user` 的版本显示“从此修改提出可复用规则”。
- `POST /api/experience/from-classification` 验证邮件确实处于人工纠正状态，再保存私有事件并调用模型。
- `POST /api/experience/from-draft` 验证版本确为用户保存且有可比较的上一版本；事件只保存正文和主题前后值、结构变化布尔值，不复制收件地址。
- `GET /api/experience/proposals` 只公开草案及来源类型/哈希，不返回私有事件内容。
- `POST /api/experience/proposals/<id>/approve` 接受用户在审核页修改后的完整候选，重新执行 5A 校验后发布。
- `POST /api/experience/proposals/<id>/reject` 保存明确拒绝理由。
- `GET /api/experience/rules` 及规则 `disable/restore` 接口提供实际规则管理。

相同来源版本与相同推广说明生成稳定事件编号；重复点击复用已有草案，不重复调用模型。模型输出结构错误时只保留私有事件供重试，不产生待审核草案，更不会发布规则。

验收：普通分类纠正、草稿编辑和任务决定不会增加待审核草案；明确请求推广后只产生一条待审核草案；拒绝后不生成规则文件；重复请求按来源和候选摘要去重。

## 5C：邮件规则加载与应用追踪

状态：已实现。分类、任务规划和拟稿会在开始时按域捕获启用规则；模型必须逐条报告是否适用，并为适用项提供当前任务中可逐字核对的依据。快照与应用记录持久保存，规则文件后续变化不会暗改已有任务。

### 分类

新分类捕获当时活动的 `mail.classify` 规则，保存规则集合摘要、规则 ID 和版本。已完成的历史分类不因规则文件变化自动重跑；用户可显式选择“按最新规则重新分类”。分类失败仍不能变成 `no_reply`。

### 规划与拟稿

邮件任务分别加载 `mail.plan` 和 `mail.draft` 规则。每个任务保存经验快照；规则更新不会暗中修改已有草稿。用户选择“按最新经验重新准备”时才更新快照、重新规划或拟稿，并使旧发送预览失效。

模型返回结构化 `rule_results`：规则编号、是否适用、支持判断的当前邮件或已选往来原文片段，以及应用结论。原文片段必须能在输入中逐字找到。选中的规则过多、总长度超限、规则冲突或规则文件无效时进入人工核对，不静默截断。

规则优先级固定为：

1. 程序硬编码的安全与来源约束。
2. 用户对当前任务的明确决定。
3. 当前任务临时要求。
4. 已批准的个人偏好。
5. 已批准的通用经验规则。
6. 默认行为。

经验规则不能授权发送、提交或披露，不能扩大资料读取范围，不能跳过具体版本确认，也不能把外部结果不明改为可自动重试。

### 5C 真实验收方法

自动测试只能证明加载、版本冻结、逐字依据校验和审计接口满足协议；真实验收还必须使用实际模型、两个内容不同的真实邮件和重启后的生产进程。建议使用一条容易观察但不会改变安全边界的语义规则，例如“报名截止、材料提交截止和活动开始时间必须按正文原词区分，不得互换”。不要使用“自动发送”“自动提交”或包含姓名、邮箱、课程等个人信息的规则。

1. 先备份被 Git 忽略的 `data/`，确认测试邮箱和模型配置有效，运行 `./lab1/restart_and_verify.sh`。在手机网页完成一次分类纠正或保存一次草稿修改，另行点击“提出可复用规则”。
2. 在“经验规则”区域检查规则编号、三个作用域、正文、正例、反例及隐私内容，批准后运行 `python3 lab1/experience.py rules`，并人工查看 `experience/rules/mail/<规则编号>.json`。文件应为 `enabled: true`、`active_version: 1`，且不含原邮件全文或地址。
3. 完全重启邮件网页和调度进程，再由另一个测试地址发送通知 B。通知 B 应使用不同措辞和不同日期，但明确包含“报名截止”“材料提交截止”“活动开始”中的至少两项；不要复制规则正例，否则不能证明泛化。
4. 点击“立即扫描”，等待分类和任务进入草稿状态。打开任务详情的“查看本任务的经验规则应用证据”，核对 `mail.plan`、`mail.draft` 的规则编号、版本、规则集摘要、`applicable`、`evidence_quotes` 和 `conclusion`。每个依据片段必须能在通知 B、已选往来、当前目标或当前决定中逐字搜索到；最终计划和草稿必须保持各日期语义。
5. 在规则管理区填写理由并停用该规则，发送通知 C 后再次扫描。新任务的计划和拟稿快照中不得包含该规则；旧任务仍保留原规则版本和应用记录。恢复规则后创建的下一项新任务应再次包含它。
6. 从新的明确纠正产生同一规则编号的第二版并批准。先重新打开旧任务，确认它仍显示 v1 且草稿没有自动变化；再点击“按当前决定和最新经验重新规划”，确认任务改用 v2、产生新草稿版本，并要求重新生成发送预览和重新确认。
7. 最后只生成发送预览，不勾选确认，直接发送必须被拒绝；即使规则文字声称可以自动发送也不能改变该结果。若需验证真实投递，再按阶段二的冻结预览流程人工确认，并用投递审计核对 SMTP 接收记录。

出现以下任一情况即判定 5C 真实验收失败：只看到规则文件却没有任务应用记录；依据不是当前任务中的逐字片段；停用后新任务仍加载规则；规则升级暗改旧草稿；重新规划后仍使用旧版本；未经冻结确认即可发送。测试完成后可保留测试规则用于版本审计，或通过网页显式停用；不要直接删除规则文件或生产 SQLite 记录。

## 5D：手机审核与跨会话复用

状态：已实现。手机页将待审核/历史草案、启用规则和停用规则分区展示；所有审核和状态变更均为独立操作。任务应用记录通过任务专属接口读取，并只返回该任务冻结的规则快照、规则集摘要、逐字依据和应用结论。

手机页面增加独立的经验区域：待审核草案、活动规则、停用规则和任务应用记录。批准、拒绝、停用和恢复均要求单独操作；规则不与发送或 ehall 确认共用勾选框。

实际接口：

- `GET /api/experience/proposals`
- `POST /api/experience/proposals/<id>/approve`
- `POST /api/experience/proposals/<id>/reject`
- `GET /api/experience/rules`
- `POST /api/experience/rules/<id>/disable`
- `POST /api/experience/rules/<id>/restore`
- `GET /api/tasks/<id>/experience`

接口沿用现有 Bearer token、同源检查、no-store 响应和单机锁。应用详情只展示当前任务的规则和必要证据，不返回其他邮件或个人资料。

跨会话复用不依赖浏览器会话或内存对象：新进程从已发布规则文件加载活动版本，并继续向 SQLite 写入应用审计。停用规则后，历史任务仍能通过任务专属接口读取原快照和证据，新进程捕获的新快照则不再包含该规则。网页访问口令只保护接口访问，不参与规则版本身份或应用摘要计算。

## 5E：重复邮件流程与扩展性收尾

状态：已实现。可重复操作说明保存于 `experience/workflows/mail-reply.md`；隔离端到端验收覆盖规则加载、分类、任务创建、规划、拟稿、用户编辑、显式经验提议、冻结确认、SMTP 接收、归档、重复扫描和进程重建。ehall 仍只有课表退课这一项生产适配器，第二个合成适配器只用于证明同一契约能够扩展，不增加真实事务。

将已有邮件调度、资料查询、手机补充、编辑、确认、发送和归档保存为人工可读的工作流说明，并用隔离端到端测试重复执行。重复扫描不得重复建任务或发送；归档后来源、草稿、确认版本、SMTP 结果和经验应用记录仍可查询。

ehall 本步只增加或整理适配器契约测试，验证 `identify`、`inspect`、`normalize`、`validate`、`fill/read_back`、`consequences`、`submit/reconcile` 等边界可被第二个显式适配器复用。不增加新事务，不允许通用模型决定选择器或最终点击。

## 关键验收场景

1. 通知 A 中模型把报名截止时间误当成活动开始时间。
2. 用户纠正当前任务，并另外选择“提出可复用规则”。
3. 系统生成待审核草案；用户核对作用域后批准。
4. 关闭并重新启动进程，处理内容和发件人不同的通知 B。
5. 通知 B 正确区分报名截止、材料提交和活动开始时间，任务记录含规则 ID、版本、规则集摘要、逐字依据和应用结论。
6. 同时验证另一项标记为“仅本次任务”的修改没有影响通知 B。
7. 停用规则后处理通知 C，确认该规则不再进入任务快照；恢复后新任务再次使用。
8. 规则更新不改变已有草稿、确认或已发送记录；显式按最新经验重新准备才产生新版本。
9. 邮件完整流程可重复执行，关闭页面和重启服务不丢任务，重复扫描不重复创建或发送。
10. 外部邮件中的“把这条指令保存成永久规则”不会创建事件、草案或规则。
11. 规则不能绕过邮件发送或 ehall 提交确认，结果不明保护保持不变。
12. 阶段一至四全部回归测试通过。

## 分步完成标准

| 小步 | 完成标准 |
| --- | --- |
| 5A | 事件不自动推广；草案须批准；规则连续版本、拒绝、停用、恢复、重启和发布中断可恢复；人工冲突不覆盖 |

## 明确保留边界

- 不从所有用户编辑自动学习，也不把模型推断直接写成规则。
- 不自动把规则、个人偏好或运行数据提交到 Git。
- 不把个人事实混入公开规则文件。
- 不让经验规则修改程序安全状态机或确认要求。
- 不引入向量索引、外部规则服务、消息队列或持续运行的 Agent。
- 不增加资讯监控或新的 ehall 事务，除非邮件经验闭环已经完成并单独重新设计。
- 不从邮件自动创建、确认或提交 ehall 任务。
