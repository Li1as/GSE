# 第一阶段：个人资料检索与文本补充

## 范围与当前进度

按照最新约定，只对当前 用户指定的简历与成绩单合并 PDF 做一次性文本转换和人工整理。原件不修改，不建设通用 PDF/DOCX 导入器、OCR 服务、文件去重系统或多格式索引流水线。

后续新增个人信息只接受 Markdown 或输入框文本。资料仅涉及一个人，检索使用分类、关键词子串匹配和少量别名，不使用向量索引、Embedding 或向量数据库。

当前 A、B、C、D 均已实现并在约定的单机范围内验收。执行与验收入口见 [README.md](README.md)。

## 小步 A：一次性资料整理（已完成）

整理结果位于本地 `data/personal/`：

| 文件 | 内容与用途 |
| --- | --- |
| README.md | 分类目录与来源定位说明 |
| resume.md | 简历六类栏目，保留全部项目和实践经历 |
| transcript.md | 按学期排序的课程成绩表、汇总与分数口径 |
| issues.md | 日期异常、评分口径、时效和提取限制 |
| source.md | 按 PDF 第 1—5 页保存的原始提取文本与来源哈希 |

一次性处理包括：合并版面换行、重排成绩单左右栏、衔接跨行课程名、规范 `.25` 为 `0.25`，以及对照页面修复提取乱码。课程按“学期＋课程号”保留；不同学期同名课程不去重。“通过”保持文本，“退选”保持备注且不填零分。异常日期不自动推测修正。

首次资料直接作为 Markdown 数据来源，不另外建立字段事实数据库。source.md 是核对材料，不能与整理后的内容算作两份独立证据。资料量很小，可通过文件标题、表格行和原 PDF 页码定位。

个人资料目录默认被 Git 忽略；实现、设计、别名和空配置示例可以纳入版本管理。原 PDF 保留原位，本地 Markdown 构成之后迭代的资料基础。

## 模型配置约定

配置示例见 [config.example.json](config.example.json)：

- `api_url`：示例为空，本地已使用用户提供地址。
- `api_key`：示例为空，本地已使用用户提供凭据，不进入 Git。
- `model`：固定填写 `gpt-5.6-terra`，不替换为其他型号。
- `api_protocol`：`chat_completions`，使用 `/v1/chat/completions`；通过 JSON 动作协议执行工具，不依赖原生 function calling。
- `personal_data_dir`：`data/personal`，相对于 lab1 目录。

运行配置为 `config.local.json`，该文件被 Git 忽略且权限为 600。模型列表和实际请求均在用户指定服务验证。配置缺失时清楚报错；不默默切换服务或模型。请求不自动跟随重定向，不输出可能回显凭据的远端错误正文。

## 小步 B：API 检索与来源回答（已实现）

先提供命令行入口，核心接口设计为 `query(text)`、`get_task(task_id)`，后续手机和 smail 复用业务模块。

流程：接收自然语言 → 保存任务目标 → 模型拆解需求与关键词 → 程序按分类和子串检索 → 必要时读取上下文 → 模型返回答案、引用、缺失项与冲突项 → 程序校验并保存。

模型通过用户配置的 API 调用；本地程序提供 `list_sources`、`search_personal_info`、`read_evidence` 等受限工具。模型不直接拥有文件系统或 Shell 权限。采用经程序校验的 JSON 动作协议并请求 JSON 输出；格式不合法时最多重试一次，仍计入总步骤限制。默认单次请求超时 45 秒、最多 8 步、单次输出上限 2500 tokens，执行异常不等于资料缺失。

初始检索规则：

1. 以 Markdown 文件、二级标题和成绩表行为检索单位；识别成绩表表头并随结果返回。
2. 关键词做大小写归一和必要的空白规范化；用 [retrieval-aliases.json](retrieval-aliases.json) 扩展少量明确别名，不将同方向的不同课程当成同义词。
3. 优先匹配分类、标题、课程名和课程号，再匹配正文。首次未命中可换词或扩大类别。
4. 引用带文件名、标题／行号和内容版本；课程记录包含学期与课程号。返回前校验引用确实存在，语义是否支持答案仍需验收。
5. 成绩以成绩单为依据，项目评分与课程总评分开。相关查询携带 issues.md 中的约束，不能将所有警告忽略后给出肯定答案。
6. 一次只向模型提供任务必要片段。source.md 保留本地人工回查，当前搜索不重复返回原始提取文件，read_evidence 只能重读已经返回的片段。

当前实现每次 query 重读 Markdown 并计算文件哈希；项目标题和缩进说明作为同一片段，成绩表行带表头。搜索每页最多 8 项，支持 offset 分页。别名采用精确词组扩展，category 为文件名或标题子串。每条最终答案至少引用一条实际读过的证据，程序校验引用身份，不能机械证明答案语义完全正确；仍需案例验收。判定资料缺失前至少两次不同检索。任务状态和来源文本存入 SQLite，可以离线查询；不保存密钥或完整 HTTP 请求。

## 小步 C：Markdown／文本补充与继续任务（已实现）

接口概念为 `answer_request(request_id, text, scope)`；scope 区分本次任务和长期资料。粘贴 Markdown 与普通输入框文字进入同一流程，不处理二进制附件。

SQLite 保存任务、请求和结果状态；`data/requests/` 下的 Markdown 是可读投影。请求包含编号、所属任务、缺失字段、用途、已查范围、状态。用户若通过编辑 Markdown 回答，程序需显式校验导入，不能让文件与数据库成为两个互不一致的状态源。

补充后先检查是否回答了缺失问题。有冲突则追问；有效长期信息整理到独立补充 Markdown，记录来源和时间；临时回答留在任务上下文。关联任务在补充成功后重新检索并继续，而不是开启一个无关的新任务。此阶段“自动归档”只处理文本，不重写原 PDF。

实现使用 `get_request(request_id)` 和 `answer_request(request_id, text, scope, confirm_conflict=False)`。请求文件包含原目标、缺失项、用途、已检索范围和回复标记；填入内容经显式提交进入相同业务接口。

模型只判断相关性、冲突并摘录原文，程序拒绝不在用户回复中的“摘录”。无关回复保留反馈，不改变任务等待状态；冲突必须显式确认。一次有效补充消耗原请求，部分补充续答后若仍缺信息则生成后续请求。临时补充作为当前任务的可引用证据加入检索，不写入个人资料目录。

请求接受记录与任务补充记录在一个 SQLite 事务中保存，再按请求编号写入固定 Markdown 文件，之后以相同任务编号重新检索。重复相同回复使用内容回执去重；接受后续答失败可以原样重试，重新构建缺失的归档文件。记录旧答案与搜索轨迹，避免把失败续答和旧成功结果混为一谈。

本次两项成绩作为用户文本补充保存；不为新课程推测课程号或学分，不把“计算机程序设计语言”并入名称相似的其他课程。完整验收见 [stage1-c-acceptance.md](stage1-c-acceptance.md)。

## 小步 D：文本更新与重启恢复（已实现）

启动和查询前扫描 Markdown，利用内容哈希识别变化；文件不多，无需专门索引服务。修改、删除后重建对应片段，已保存的历史结果保留其来源版本，但不能作为最新事实直接复用。

持久化任务目标、阶段、证据、待补充请求与结果。重启后从持久状态重建模型上下文，无需保留一个长期运行的聊天窗口。补充采用稳定请求编号防止重复归档；资料写入与状态更新中途失败时可识别未完成操作并恢复。

实现位于 [persistence.py](persistence.py) 与 assistant.py：

- 保存每次查询读取的文件哈希清单；输出前再检查清单，发现变化即拒绝发布旧快照回答。历史结果查询时标记 freshness，保留原引用原文。
- `recover()` / CLI worker 扫描中断的 running 任务、可重试失败和资料已变化的 waiting_input 任务。从持久目标、已接受补充及当前文件重新运行有界检索，不恢复旧 HTTP 会话。
- task lock 使用 Linux flock；查询、接受补充和恢复共用同一任务锁。不同任务可并行，同一任务不会被多个进程同时执行。强制终止释放锁。
- 新增 archives 表作为归档待办，接受记录与任务补充在同一 SQLite 事务提交。文件发布完成才标为 published。中断后可以补文件，或识别“文件已写、状态未更新”。
- published 文件由用户管理，修改／删除不被重复回执或恢复器还原。旧版 C 收据迁移为 published；无法从旧版日志判断的历史删除不擅自恢复。
- 请求编号与任务关联同事务保存；恢复补齐投影、保留草稿，避免孤立请求和重复追问。
- 网络类失败采用退避与最多三次执行尝试；认证、协议等错误保留失败供人工处理。显式 resume 可重置预算。未变化的等待状态不调用模型。

持续恢复依赖用户运行 worker，未安装开机启动服务。它是单机协调方案，不包含多主机分布式锁或数据库损坏后的备份恢复。文件版本校验说明回答依据哪个快照，不阻止用户在回答发布后继续修改资料。

典型状态：待处理 → 检索中 → 等待补充／等待核对 → 检索中 → 已完成；另有可恢复失败和取消。不得用模型/API 超时触发“缺少个人资料”的追问。

## 各小步验收边界

| 小步 | 验收 |
| --- | --- |
| A | 简历完整栏目、成绩单全部课程、来源页码；视觉核对左右栏与异常分数；不调用模型 |
| B | 自然语言不同问法可返回正确证据；不存在的信息不编造；缺配置和 API 异常有独立错误 |
| C | Markdown／文本补充后恢复原任务；无关回复不误解锁；临时回答不污染长期资料 |
| D | 修改／删除后不引用过时内容；重启不丢任务；同一补充不重复归档 |

A 的归档验收见 [stage1-a-acceptance.md](stage1-a-acceptance.md)；B 的 API 与检索验收见 [stage1-b-acceptance.md](stage1-b-acceptance.md)；C 的补充验收见 [stage1-c-acceptance.md](stage1-c-acceptance.md)；D 的恢复验收与阶段总结见 [stage1-d-acceptance.md](stage1-d-acceptance.md)。
