# 阶段二：邮件准备、手机交互与确认发送

本阶段从手动选定一封邮件开始，完成读取往来、检索个人资料、追问补充、生成草稿、手机编辑确认、发送与归档。持续收信和自动分类属于阶段三。监控、转发与状态恢复由脚本承担；模型只在需要理解和拟稿时调用。

## 模块与数据边界

1. 邮件连接器：Python 标准库 `imaplib`、`email` 读取邮件；发送阶段再引入 `smtplib`。登录协议以学校官方说明和实际账号验证为准，网页微信扫码不等于 IMAP 可直接使用网页登录密码。
2. 邮件任务管理：独立的父任务关联阶段一资料查询子任务，SQLite 保存状态。复用阶段一查询、补充及恢复能力，不把邮件业务塞入资料查询器。
3. 草稿生成：复用现有 API 配置和 `gpt-5.6-terra`，只提供选中邮件、必要往来和有来源的资料。邮件属于外部输入，其内容不能授权发送、修改本地规则或泄露其他资料。
4. 手机网页：响应式任务列表、补充表单、草稿编辑和确认页。初期使用有身份校验的局域网入口，业务状态保存在后台，关闭网页不会丢失任务。具体 Web 框架在 2C 选定。

邮件快照保存账号、文件夹、UIDVALIDITY、UID、Message-ID、In-Reply-To、References、参与人、日期、正文和附件元信息。IMAP 身份使用账号＋文件夹＋UIDVALIDITY＋UID；Message-ID 用于往来关联，不能单独承担采集去重。快照和凭据位于 Git 忽略范围。

会话关联优先使用回复头字段；主题相同不代表同一会话。限制头部扫描和正文读取数量，明确标识不完整历史，后续按需读取已发送文件夹。HTML 转为文本，不加载远程资源；附件初期保留原始邮件和元信息，不自动执行或解析附件。

## 小步 2A：验证接入并只读获取邮件

目标：验证真实账号登录，人工选定一封邮件，读取正文及相关邮件头候选，保存可追溯快照。

- 配置独立 `mail.local.json`；示例不含账号密码。验证 TLS 证书，连接设超时，认证失败不循环重试。
- CLI `probe` 验证 IMAP 登录，`list` 列最近邮件头，`read UID` 保存一封原始邮件和 JSON；`thread UID` 在有界窗口寻找关联头部候选。
- 使用只读 EXAMINE 与 BODY.PEEK，不标已读，不移动、删除或发送邮件。
- 单封上限 10 MiB，最近头部窗口最多 100 封；先查大小再取内容。SEARCH ALL 仍返回当前文件夹 UID 列表，后续大邮箱可优化为增量游标。
- 本步不调用模型、不启用持续监控、不验证 SMTP 发信。真实验收要求登录成功、选定 UID 可读取、快照正确、读取前后未读标志保持不变。

## 小步 2B：邮件父任务与资料子任务

状态：已实现并验收，运行入口见 [README](README.md)，测试结果及当前限制见 [2B 验收记录](stage2-b-acceptance.md)。

邮件父任务保存目标、快照引用、子任务编号、缺失项和准备状态。信息提取输出结构化需求，再逐项调用阶段一资料查询。事实缺失使用现有补充流程；“是否参加”“愿意提供哪些资料”等决定单独等待用户，不从成绩或简历推断意愿。

子任务 completed 后核对来源 freshness；waiting_input 时展示关联问题；needs_review 或 failed 不能视为资料齐全。长期补充与本次临时回答继续隔离。脚本按持久化父子关系恢复流程，生成草稿记录模型输入中的来源与使用版本。

验收：虚构通知缺一项事实和一项决定，补充后恢复原邮件任务；无关回复不解除等待，多个邮件任务不串用临时回答。草稿不编造缺失事实。

## 小步 2C：手机查看、补充与编辑

状态：网页与接口已实现，运行方式见 [README](README.md)，自动验证与真机验收边界见 [2C 验收记录](stage2-c-acceptance.md)。

提供邮件选择、任务进度、追问和草稿编辑页面。后台保存每次草稿修订，编辑提交带当前版本；旧页面覆盖新版本时返回冲突。页面刷新、手机断线和后台重启后可继续。

验收：手机能完整处理缺失项并编辑草稿，桌面可见同一版本；输入错误有明确反馈；关闭页面不影响任务持久化。本步先不提供实际发送入口。

## 小步 2D：具体版本确认与发送

状态：实现与自动回归完成，真实发送已获用户确认，SMTP 接收与冻结内容已核对。已发送目录未观察到该次相同 Message-ID 副本，本地归档完整，见 [2E 最终验收](stage2-e-acceptance.md)。

确认记录绑定任务、草稿版本、To/Cc/Bcc、主题、正文及附件内容哈希；地址解析后的最终收件人和回复目标必须展示。编辑或附件变化使原确认失效。发送程序只使用已确认快照，确认后不再调用模型改写。

发送意图、确认版本、生成的 Message-ID、尝试次数和服务响应独立保存；事务和单机锁避免双击并发发送。SMTP 前后不能用本地数据库实现跨服务原子提交。状态区分：待确认、已确认、发送中、明确失败、SMTP 已接收、结果不明。断线可能发生在服务接受之后，此时进入结果不明，核对已发送邮件或交给用户判断，不能直接重发。Message-ID 本身不能保证服务端去重。

SMTP 接收不等于最终投递或已读。验证腾讯是否自动保存已发送副本；在确认实际行为前不盲目追加副本。归档保存精确版本和响应，不仅标记“成功”。

验收：未确认不能发送；编辑后必须重新确认；重复点击只触发一次尝试；模拟发送后断线不会自动重发。真实发送仅针对用户明确批准的测试收件人和内容。

## 小步 2E：完整流程与异常验收

状态：已完成约定范围的全流程、异常回归及真实发送归档，详见 [2E 验收与完成评估](stage2-e-acceptance.md)。

用可控制的测试邮件走完读取、缺信息、补充、草稿、编辑、确认、发送和回执归档。覆盖认证过期、API 失败、断线重启、草稿并发修改、附件改变和发送结果不明。完成后再进入阶段三的持续收信与分类。

这一路径体现课程的小步反馈与可复用流程：先验证实际工具能力，再扩展任务编排；每步同时保留实现、验收证据和限制。用户纠正是否成为长期事实、偏好或可复用技能，在后续经验沉淀阶段分别处理，不将一次性邮件编辑直接写成 AGENTS.md 规则。

## 南京大学 smail 接入依据

[学校信息化中心：学生邮箱客户端配置办法](https://itsc.nju.edu.cn/1a/8f/c21586a334479/pagem.htm) 指定完整邮箱地址作为账号，IMAP SSL 使用 `imap.exmail.qq.com:993`，SMTP SSL 使用 `smtp.exmail.qq.com:465`。启用微信安全验证的账号需要客户端专用密码，并开启相应客户端服务。

使用者在 `https://mail.nju.edu.cn` 完成微信扫码，在设置的客户端设置区域开启 IMAP 服务并生成客户端专用密码，填入本地配置的 password 字段。SMTP 到发送阶段再验证。无需让后台保存微信登录 Cookie，也不需要关闭微信验证。具体界面与服务权限以账号实际页面为准。
