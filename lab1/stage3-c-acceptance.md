# 小步 3C 验收记录

## 完成范围

3C 已完成稳定收件来源与邮件任务的一对一绑定，自动和手动入口统一去重，分类变化更新并暂停同一任务，暂停后禁止生成发送预览。无历史邮件采用简洁、礼貌、偏正式且跟随主要语言的单次任务风格；程序不推断关系，不自动添加签名、联系方式、表情或整段引文。混合或无法判断语言时只询问一次语言和正式程度。长期风格学习仍属于阶段五。

同一 IMAP 完整身份由账号端点、文件夹、UIDVALIDITY 和 UID 组成。内容哈希相同但 UID 不同的两封邮件不会被错误合并。任务创建与来源绑定在同一事务及来源锁内完成，重复运行和入口切换均复用已有任务。

## 首次真实验收失败与修复

首次隔离真实 API 验收停在 `waiting_input`，没有生成草稿。模型规划生成了一条风格问题：

> 请确认本次简短确认回复使用中文、英文或其他语言，以及希望采用的正式程度。

程序同时加入固定问题：

> 请确认本次回复使用中文、英文或其他语言，以及希望采用的正式程度。

两者语义相同但文字不同，原来的精确字符串去重没有识别。验收脚本因此看到两个未回答决定，未按“只有一个固定风格问题”的条件自动回答；随后脚本直接读取尚不存在的 `draft`，又触发 `KeyError`，掩盖了前面的真实失败。

修复分三层：

1. 提示模型不要生成或改写由程序管理的 `style.decision_question`。
2. 程序按风格语义过滤模型生成的语言、正式程度、语气等重复决定，再只加入保存的固定问题；确定性约束不依赖模型是否遵守提示。
3. 真实验收脚本在草稿不存在时安全报告任务状态，不再以 `KeyError` 覆盖根因。

新增回归用例验证模型返回同义改写时，最终仍只有一个完全一致的风格问题。

## 验收结果

修复后的隔离真实 API 验收共 16 项通过：真实分类完成；人工改判后创建并绑定唯一任务；风格持久化；生成简短草稿；不推断关系、不泄露邮箱、不添加表情或签名；主题不出现重复 `Re:`；重复运行不再次调用模型；分类改回无需回复后暂停同一任务并阻止发送预览；没有生成发送记录，也没有发送邮件。

该次真实验收调用模型 4 次，生成的草稿为 11 个字符。私有报告保存在被 Git 忽略的 `data/pipeline-acceptance/` 下。

最终完整自动回归为 159 项通过；其中 `test_mail_pipeline.py` 13 项、`test_mail_tasks.py` 16 项。Python 编译、前端 JavaScript 语法与 `git diff --check` 均通过。

因此，按第三阶段设计中 3C 的边界，3C 已全部完成。3D 的往来更新与旧预览失效、3E 的持续调度和手机分类队列尚未实现，不属于 3C 完整性的缺口。
